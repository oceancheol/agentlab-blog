`DESIGN.md`는 한마디로 말하면 **AI가 디자인 의도를 바로 이해할 수 있게 해주는 마크다운 기반 디자인 시스템 문서**야.

디자인 가이드가 보통 JSON이나 Figma 파일에만 있으면, AI가 읽고 바로 적용하기가 번거로운 경우가 많아. `DESIGN.md`는 텍스트 한 장으로 색상, 타이포, 간격, 컴포넌트 규칙까지 담아둬서, AI에게 “이 프로젝트의 규칙서”로 그대로 전달할 수 있어.

## 왜 생겼을까

요즘 AI가 코드를 직접 짜는 데 익숙해지면서 문제는 이렇게 바뀌었어.

- AI는 빠르게 만들어도, 디자인 일관성이 깨질 수 있음
- 개발자/디자이너가 같은 기준을 공유하지 못함
- 툴마다 디자인 해석이 달라 결과가 들쭉날쭉해짐

`DESIGN.md`는 이걸 줄이기 위한 방식이야. 복잡한 바이너리 포맷이 아니라 **사람이 읽는 문서 + AI가 읽는 문서**를 한 번에 만든 거라고 보면 돼.

## 핵심은 한 파일에 정리한다는 것

DESIGN.md 안에는 보통 이런 항목이 들어가.

- 색상(Primary, Neutral, Semantic) 규칙
- 폰트/타이포그래피 규칙(크기·두께·행간)
- 간격 시스템(패딩, 마진, 갭 기준)
- 컴포넌트 패턴(버튼, 카드, 입력폼 스타일)
- 에levation(그림자/깊이감) 규칙
- 사용 규칙(Do/Don't)

![DESIGN.md의 핵심 구성 요소](/images/posts/designmd-components.jpg)

AI가 한 번 읽으면, 새로운 화면을 만들 때 “어떤 버튼이 어떤 색인지”, “텍스트 크기는 어떻게 설정해야 하는지”를 바로 반영할 수 있어.

## 왜 유용한가

장점은 실무에서 바로 보인다.

### 1) AI가 잘 이해한다

DESIGN.md는 YAML/JSON처럼 스키마를 맞출 필요가 없어. 그냥 마크다운 텍스트라서 AI가 컨텍스트로 쓰기 쉬워.

### 2) 버전 관리가 쉽다

한 번 정해 둔 규칙도 시간이 지나면 바뀌어. 텍스트 파일이라 git으로 변경 이력 관리가 가능해.

### 3) 벤더 락인 줄인다

특정 툴에 종속되지 않고 Claude Code, Cursor, Copilot 같은 다양한 에이전트가 참고할 수 있어.

### 4) 사람과 팀 모두가 읽는다

디자이너와 개발자가 같은 문서를 함께 볼 수 있다는 점이 가장 중요해. 형식이 단순해서 리뷰가 쉬워.

## 언제 쓰면 좋나

이게 잘 맞는 경우는 이런 팀이야.

- AI 코딩 비율이 높은 팀
- 디자인 일관성이 중요한 서비스
- 제품의 UI 톤을 문서로 고정해두고 싶은 조직
- 프로젝트에 여러 도구를 쓰는 개발 조합이 있는 곳

## 도입 방법

실제로 시작할 때는 이렇게 하면 돼.

![DESIGN.md 운영 워크플로](/images/posts/designmd-workflow.jpg)

1. 프로젝트 루트에 `DESIGN.md` 생성
2. 색상, 타이포, 간격, 컴포넌트 규칙 최소 3~5개 항목으로 작성
3. AI에게 “이 문서를 기준으로 UI를 만들어줘”라고 요청
4. 생성물마다 규칙 위반 여부를 리뷰해 반복 개선

한 번에 완벽할 필요는 없어. 처음엔 가볍게 시작해서 점점 채워가는 게 좋아.

## 주의할 점

`DESIGN.md`를 만들었다고 끝이 아니야.

- 문서가 오래되면 AI가 틀린 스타일을 반복 적용할 수 있음
- 팀 룰이 바뀌면 문서도 즉시 업데이트돼야 함
- 너무 상세하면 오히려 느려질 수 있어(필요한 만큼만 쓰는 게 핵심)

즉, 문서 유지가 핵심이다.

## 한 줄 요약

`DESIGN.md`는 AI에게 전달할 수 있는 디자인 시스템 “기본 규칙서”야.

한 줄로 정리하면, UI 일관성을 유지하는 데 쓰는 **가벼운 문서형 디자인 언어**라고 보면 돼.

## 핵심 정리

- 마크다운 기반으로 디자인 의도와 규칙을 정리한다
- AI가 바로 읽고 적용하기 쉬운 형태다
- 변경이력 관리가 가능하고 팀 협업에 유리하다
- 툴에 종속되지 않고 재사용성이 높다
- 초기에 최소 규칙부터 시작해 점진적으로 확장한다
