`gstack`은 Claude Code를 여러 역할로 나눠 쓰게 해주는 오픈소스 슬래시 커맨드 모음이야. 단순히 코드를 대신 써주는 도구가 아니라, 기획부터 배포까지 이어지는 개발 흐름을 한 번에 정리해주는 게 핵심이야.

Garry Tan이 만들었고 MIT 라이선스로 공개돼 있어서, 누구나 자유롭게 쓸 수 있어.

## gstack이 무엇인지

gstack의 목적은 Claude Code를 하나의 에이전트가 아니라 **가상 엔지니어링 팀**처럼 쓰게 만드는 거야.

예를 들면 이런 식이야.

- 기획을 다시 묻는 역할
- 엔지니어링 관점에서 설계를 검토하는 역할
- 디자인을 점검하는 역할
- 버그 원인을 추적하는 역할
- QA 브라우저 테스트를 수행하는 역할
- 배포 후 상태를 확인하는 역할

즉, 사람 한 명이 모든 판단을 떠안는 대신, 각 단계마다 다른 시선으로 검증하게 만드는 구조야.

## 개발 스프린트 흐름

gstack은 기본적으로 다음 순서로 움직여.

생각 → 계획 → 빌드 → 리뷰 → 테스트 → 배포 → 회고

이 흐름이 좋은 이유는 단순해. 바로 코딩부터 시작하지 않기 때문이야. 먼저 문제를 다시 정의하고, 그다음 설계를 맞추고, 마지막에 구현과 검증으로 넘어가게 해줘.

## 전체 커맨드 구조

gstack의 커맨드들은 대체로 단계별로 나뉘어 있어.

### 1단계: 기획과 전략

이 구간에서는 문제를 다시 정의하고, 제품 방향을 다듬어.

- `/office-hours`: 6가지 핵심 질문으로 제품 방향을 재정의하는 시작점
- `/plan-ceo-review`: CEO/창업자 관점에서 문제를 다시 생각하는 단계
- `/autoplan`: CEO, 디자인, 엔지니어링 리뷰를 한 번에 자동으로 돌리는 흐름

여기서 중요한 건 “무엇을 만들지”를 먼저 선명하게 하는 거야.

### 2단계: 설계와 아키텍처

이 구간에서는 구현 전에 구조를 맞춰.

- `/plan-eng-review`: 아키텍처, 데이터 흐름, 에러 경로를 정리
- `/plan-design-review`: 시니어 디자이너 관점에서 계획을 점검
- `/design-consultation`: 디자인 시스템을 처음부터 정리하는 단계

이 단계는 나중에 고치는 비용을 줄여줘. 구조가 애초에 엉켜 있으면 코딩 속도가 아니라 수정 속도가 문제되거든.

### 3단계: 개발 중 디버깅

- `/investigate`: 원인 파악 없이 수정하지 않는 디버깅 흐름

이 커맨드의 핵심은 무작정 패치하지 않는 거야. 실패 원인을 먼저 좁히고, 같은 실수를 반복하지 않게 만드는 데 초점이 있어.

### 4단계: 리뷰

- `/review`: 스태프 엔지니어 관점의 리뷰
- `/codex`: OpenAI Codex CLI를 통한 독립적 코드 리뷰
- `/design-review`: 시각적 불일치와 간격 문제까지 점검

여기서는 “작동한다”와 “좋다”를 분리해서 봐야 해. 돌아가는 코드와 잘 만든 코드는 다르니까.

### 5단계: QA와 테스트

- `/qa [URL]`: 실제 브라우저로 테스트하고 수정까지 수행
- `/qa-only [URL]`: 테스트만 수행하고 리포트 작성
- `/browse`: 실제 Chromium 브라우저로 클릭과 조작 수행
- `/benchmark`: 성능 측정
- `/cso`: 보안 감사

이 단계는 배포 직전의 마지막 방어선이야. 특히 브라우저 기반 QA는 실제 사용 흐름을 확인할 수 있어서 꽤 실용적이야.

### 6단계: 배포

- `/setup-deploy`: 배포 플랫폼 자동 감지
- `/ship`: main 동기화부터 PR 생성까지
- `/land-and-deploy`: 머지 후 배포 검증까지 한 번에
- `/canary`: 배포 후 이상 징후 모니터링

배포 단계의 장점은 실행 흐름이 명확하다는 거야. 무엇을 언제 확인해야 하는지 흐트러지지 않아.

### 7단계: 마무리

- `/document-release`: README, CHANGELOG 같은 문서 정리
- `/retro`: 회고와 통계 분석

개발은 끝났는데 문서가 비어 있으면 다음 사람이 고생해. 그래서 마무리 단계가 따로 있다는 점도 좋다.

## 안전장치도 따로 있다

gstack은 위험한 작업 전에 멈추게 하는 도구도 제공해.

- `/careful`: 위험 커맨드 실행 전 경고
- `/freeze [경로]`: 특정 디렉토리 밖 편집 차단
- `/guard`: 경고와 편집 제한을 함께 적용
- `/unfreeze`: 제한 해제

이런 장치는 실수로 중요한 파일을 건드리는 일을 줄여줘. 특히 배포나 대규모 수정 전에 유용해.

## 실제로 쓸 때 좋은 점

gstack의 가장 큰 장점은 개발 과정을 “감”이 아니라 “절차”로 바꿔준다는 거야.

좋은 점을 정리하면 이래.

- 기획과 구현을 분리할 수 있다
- 설계 검토를 자동화할 수 있다
- 리뷰 기준을 역할별로 나눌 수 있다
- QA와 배포를 반복 가능한 흐름으로 만들 수 있다
- 안전장치가 있어서 실수를 줄일 수 있다

특히 팀 규모가 작을수록 이런 흐름이 더 유용해. 사람이 적을수록 한 명이 여러 역할을 겸해야 하니까, 도구가 그 분업을 대신해주는 셈이야.

## 설치 방법

gstack은 Claude Code에 붙여서 설치할 수 있어.

```bash
git clone https://github.com/garrytan/gstack.git ~/.claude/skills/gstack && cd ~/.claude/skills/gstack && ./setup
```

## 한 줄로 정리하면

gstack은 Claude Code를 단순한 코딩 도구가 아니라, 기획·설계·리뷰·테스트·배포까지 맡는 가상 엔지니어링 팀처럼 쓰게 해주는 도구야.

무작정 빠르게 치는 대신, 더 안전하고 더 구조적으로 일하고 싶을 때 잘 맞아.
